Architecture: Storage, Persistence & Migration

This document details the on-disk storage architectures, atomic filesystem invariants, legacy profile migration, and hardware-backed credential encryption implemented in src/main/p2p/peer-store.ts and src/main/p2p/credential-store.ts.

1. Storage Architecture Overview

All application state is saved under the platform user data directory:

  • Windows: %APPDATA%\p2p-multiple-groups\
  • macOS: ~/Library/Application Support/p2p-multiple-groups/
  • Linux: ~/.config/p2p-multiple-groups/

2. MultiGroupPeerStore (V2 Schema)

The peer profile is persisted in peer-state.json. It captures node identity, virtual group memberships, and local library file registrations.

export interface PersistedPeerStateV2 {
  version: 2
  peerId: string                            // Persistent UUIDv4
  displayName: string                       // 1-32 characters
  relayOnly: boolean                        // Global privacy mode
  groups: PersistedGroupV2[]
  sharedFiles: PersistedSharedFileV2[]
}

export interface PersistedGroupV2 {
  groupKey: string                          // JSON string [signalingUrl, groupId]
  signalingUrl: string                      // WebSocket URL
  groupId: string                           // Room identifier
  supernodeEligible: boolean
  autoJoin: boolean
  credentialCiphertext: string | null       // Deprecated legacy field; managed by SafeCredentialStore
}

export interface PersistedSharedFileV2 {
  fileId: string                            // UUIDv4
  path: string                              // Filesystem path
  groupKeys: string[]                       // Authorized group keys
}

Atomic Disk Persistence Invariants

To prevent file truncation during unexpected application crashes or power loss:

  1. State is serialized to a JSON string with 2-space indentation.
  2. The payload is written to a staging file:
    StagingPath = join(dataDir, "peer-state.json." || randomUUID() || ".tmp")
  3. Written using exclusive write flags (flag: 'wx').
  4. Atomically renamed over peer-state.json via fs.rename().
  5. Disk write operations are serialized through an internal promise queue, ensuring concurrent caller promises never interleave filesystem writes.

3. Legacy Migration Subsystem (V1 -> V2)

The application provides automatic forward migration for profiles generated by legacy V1 single-network builds (Kazaa).

Detection & Trigger

When createMultiGroupPeerStore(dataDir) executes:

  1. Reads peer-state.json.
  2. If version === 1:
    • Validates legacy schema (must have valid peerId, displayName, roomId, signalingUrl, and sharedFiles).
    • Verifies that no conflicting peer-state.v1.backup.json already exists with different contents.
  3. Backup Creation: Copies the exact V1 file bytes to peer-state.v1.backup.json before altering a single byte on disk.
  4. V2 Migration Logic:
    • Preserves peerId and displayName.
    • Derives the canonical group key:
      GroupKey = makeGroupKey(signalingUrl, roomId)
    • Converts the single room into the first entry in groups (autoJoin: false, supernodeEligible preserved).
    • Maps each entry in sharedFiles to a PersistedSharedFileV2 object, setting groupKeys: [GroupKey].
  5. Atomically commits the upgraded V2 payload to peer-state.json.

4. SafeCredentialStore Hardware Encryption

Secret access tokens for virtual groups are decoupled from peer-state.json to prevent exposure via accidental file sharing or system diagnostics.

Storage Mechanics

  1. OS-Level Key Derivation: Uses Electron safeStorage:
    • Calls safeStorage.isEncryptionAvailable() to probe native keyring support.
    • Encrypts via safeStorage.encryptString(jsonPayload).
    • Decrypts via safeStorage.decryptString(cipherBuffer).
  2. File Permissions (0o600):
    • The encrypted blob is stored in credentials.enc.
    • Staged in a temporary file with restrictive POSIX permissions: 
      await this.fileIO.writeFile(tempPath, encrypted, { flag: 'wx', mode: 0o600 })
    • Only the operating system user account executing the process can read or write the file.
  3. Graceful Memory Fallback:
    • In environments where hardware keychains are unavailable (e.g., headless Linux, CI runners, Docker containers), the store logs a diagnostic warning and retains tokens in an in-memory Map<string, string>.
    • Tokens remain accessible throughout the application session but are never written to disk in plaintext.
  4. Queue Serialization: All getCredential, setCredential, and deleteCredential calls pass through queueOperation, eliminating read-after-write inconsistencies.
