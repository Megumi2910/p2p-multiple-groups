Phần 3: Mã Nguồn Tiến Trình Main & Bộ Điều Phối P2P Engine

Khám phá chi tiết các cấu trúc logic vận hành phía hệ thống: từ kiểm soát an ninh 4 tầng của IPC, thuật toán bầu chọn Supernode HRW, cơ chế băm vân tay file siêu tốc, đến tầng truyền dẫn WebRTC đa kênh và điều khiển luồng cửa sổ trượt.

💡
Module cốt lõi

Chương này phân tích trực tiếp các file: src/main/index.ts, src/main/p2p/election.ts, credential-store.ts, peer-store.ts, library.ts, search-index.ts, signaling-client.ts, transport.ts, transfers.ts, và engine.ts.

1. Tiến trình chính Main Process & An ninh IPC (src/main/index.ts)

1.1. Khởi động, Khóa đơn phiên và Di trú Profile Kazaa

Hàm app.requestSingleInstanceLock() bảo đảm chỉ có một phiên bản ứng dụng duy nhất được chạy trên máy tính, tránh tình trạng xung đột ghi đè file dữ liệu peer-state.json. Module profile-migration.ts tự động phát hiện và di chuyển dữ liệu cấu hình từ phiên bản cũ sang phiên bản mới mà không làm mất thông tin.

1.2. Hàm thẩm định nguồn gửi validateSender: 4 tầng bảo vệ an ninh

Mọi thao tác gọi qua kênh IPC đều bắt buộc phải vượt qua 4 kiểm tra nghiêm ngặt: 

// src/main/index.ts:79-105
function validateSender(event: IpcMainInvokeEvent): void {
  // Tầng 1: Cửa sổ chính phải đang tồn tại và chưa bị hủy
  if (!mainWindow || mainWindow.isDestroyed()) {
    throw new Error('Untrusted sender')
  }

  // Tầng 2: WebContents người gửi phải trùng khớp chính xác với mainWindow
  if (event.sender !== mainWindow.webContents) {
    throw new Error('Untrusted sender')
  }

  // Tầng 3: Khung gửi tin phải là Top-Level Frame (parent === null), cấm iframe lồng
  const frame = event.senderFrame
  if (!frame || frame.parent !== null) {
    throw new Error('Untrusted sender')
  }

  // Tầng 4: Kiểm tra nguồn gốc Origin chính xác theo chế độ chạy
  if (isDev) {
    const parsed = new URL(frame.url)
    if (parsed.origin !== expectedDevOrigin || parsed.pathname !== '/') {
      throw new Error('Untrusted sender')
    }
  } else {
    if (frame.url !== productionHtmlUrl) {
      throw new Error('Untrusted sender')
    }
  }
}

1.3. Điều phối luồng và Trailing Throttle 200ms

Hàm dispatchStateToWindow sử dụng bộ hẹn giờ 200ms để gom các cập nhật trạng thái dồn dập từ mạng P2P, ngăn chặn tình trạng nghẽn kênh IPC và giúp giao diện React luôn mượt mà.

1.4. Quản lý vòng đời before-quit

Khi người dùng đóng ứng dụng, sự kiện before-quit tạm thời ngăn chặn việc thoát ngay lập tức để gọi peerEngine.dispose(), giải phóng socket và đóng kết nối WebRTC với bộ hẹn giờ bảo vệ tối đa 5 giây.

2. Bầu chọn Supernode & Băm nhất quán HRW (src/main/p2p/election.ts)

2.1. Thuật toán electSupernodes

Mỗi nhóm bầu chọn tối đa 2 Supernode dựa trên:

  1. Lọc các node có cờ supernodeEligible === true.
  2. Sắp xếp ưu tiên tăng dần theo thời điểm gia nhập (joinOrder) nhằm tối đa hóa tính ổn định.
  3. Nếu hòa điểm joinOrder, so sánh thứ tự từ điển của peerId.

2.2. Băm phân tán Rendezvous Hashing (HRW) với SHA-256

Các node bình thường (Ordinary Peers) tự động chọn Primary và Standby Supernode bằng thuật toán Highest Random Weight (HRW): 

// src/main/p2p/election.ts:44-61
const scored = electedSupernodes.map((s) => {
  // Tính điểm băm SHA-256 kết hợp giữa peerId của mình và supernodeId
  const hash = createHash('sha256').update(`${peerId}:${s.peerId}`).digest('hex')
  return { supernode: s, hash }
})

// Sắp xếp giảm dần theo mã băm hex
scored.sort((a, b) => b.hash.localeCompare(a.hash) || b.supernode.peerId.localeCompare(a.supernode.peerId))

return {
  primary: scored[0].supernode,  // Điểm băm cao nhất làm Primary
  standby: scored[1].supernode   // Điểm băm nhì làm Standby
}

Thuật toán này bảo đảm mức độ phân bổ tải đồng đều và tối thiểu hóa sự xáo trộn (Minimal Churn) khi mạng có thành viên mới vào hoặc rời nhóm.

2.3. Vòng đệm lưu trữ sự kiện phục hồi: RecoveryEventRingBuffer

Lưu giữ tối đa 100 sự kiện biến động cấu trúc mạng (thay đổi Supernode, mất tín hiệu) theo cấu trúc FIFO Ring Buffer phục vụ cho việc giám sát trạng thái trên giao diện.

3. Lưu trữ đĩa & Mã hóa phần cứng (src/main/p2p/credential-store.ts, peer-store.ts)

3.1. Két an toàn SafeCredentialStore

  • Mã hóa phần cứng: Tận dụng electronSafeStorage để gọi DPAPI trên Windows hoặc Keychain trên macOS.
  • Phân quyền tập tin: File credentials.enc được lưu với quyền bảo mật 0o600 (chỉ cho phép user hiện tại của hệ điều hành đọc/ghi).
  • Memory Fallback: Nếu chạy trên Linux không có môi trường Desktop Keyring, tự động chuyển sang lưu trữ tạm thời trong RAM.
  • Hàng đợi tuần tự: Mọi thao tác truy cập két đều được đồng bộ hóa qua queueOperation.

3.2. Sổ cái peer createMultiGroupPeerStore

Quản lý tập tin peer-state.json: tự động tạo bản sao lưu peer-state.v1.backup.json khi nâng cấp từ định dạng cũ, và luôn sử dụng cơ chế ghi đĩa nguyên tử (Atomic Write via .tmp rename) để tránh hỏng file khi mất nguồn đột ngột.

4. Thư viện chia sẻ & Chỉ mục tìm kiếm đảo ngược (src/main/p2p/library.ts, search-index.ts)

4.1. Bộ quản lý file LibraryManager

  • Giới hạn an toàn: Dung lượng tối đa 1 GiB/file, tối đa 1,000 file chia sẻ.
  • Dấu vân tay siêu tốc (statFingerprint): Lưu trữ bộ ba { size, mtimeMs, ino } để kiểm tra tính toàn vẹn khi quét lại thư viện mà không cần đọc và băm lại nội dung file.
  • Hàng đợi băm 2 luồng song song (MAX_CONCURRENT_HASHING = 2): Ngăn ngừa quá tải CPU khi chia sẻ nhiều file dung lượng lớn.
  • Cấp quyền nhóm (groupKeys): Từng file được chỉ định rõ những nhóm nào có quyền tìm kiếm và tải về.

4.2. Quản lý chỉ mục Supernode SupernodeIndexManager

Supernode duy trì cây chỉ mục đảo ngược:

  • Catalog Staging Buffer: Lưu tạm danh mục file từ node gửi với bộ đếm thời gian 5 giây (CATALOG_STAGING_TTL_MS = 5000). Nếu không nhận đủ dữ liệu trong 5 giây, bộ đệm tự hủy để bảo vệ bộ nhớ RAM.
  • Chuẩn hóa Unicode NFKC: Khử khác biệt giữa bảng mã tiếng Việt dựng sẵn và tổ hợp trước khi kiểm tra logic VÀ (Boolean AND) với hàm tokens.every().
  • Bộ nhớ đệm câu truy vấn (Query Cache): Ghi nhớ 256 kết quả tìm kiếm gần nhất trong 30 giây để phản hồi ngay lập tức.

5. Client Signaling & Tầng WebRTC gộp kết nối (src/main/p2p/signaling-client.ts, transport.ts)

5.1. Máy khách báo hiệu SignalingClient

Duy trì kết nối WebSocket tới máy chủ Signaling, kiểm tra tính đơn điệu của số thứ tự (epoch, revision) để bỏ qua các gói tin cũ đến chậm, và áp dụng thuật toán ngắt quãng lũy thừa (Exponential Backoff with Jitter) khi kết nối lại.

5.2. Quản lý truyền dẫn TransportManager

Sử dụng thư viện Werift WebRTC:

  • Gộp kết nối (Connection Pooling): Duy trì duy nhất 1 đối tượng RTCPeerConnection giữa 2 máy bất kỳ dù có cùng tham gia nhiều nhóm, và dồn kênh qua Data Channel p2p-multiple-groups-control-v2.
  • Giải quyết đụng độ Glare: Khi cả hai máy cùng gửi Offer cho nhau, máy có chuỗi localPeerId nhỏ hơn theo thứ tự từ điển sẽ nắm quyền chủ động tạo Offer, máy còn lại chuyển sang chế độ chờ.
  • Nhận diện lộ trình: Kiểm tra trạng thái ứng viên ICE để thông báo đường truyền kết nối là Direct (trực tiếp) hay Relayed (TURN).

6. Chuyển giao file & Điều khiển luồng cửa sổ trượt SCTP (src/main/p2p/transfers.ts)

6.1. Hạn mức đồng thời và Watchdog 30 giây

Giới hạn tối đa 2 upload và 2 download cùng lúc. Đồng hồ giám sát (Stall Watchdog) sẽ tự động hủy các lượt truyền bị đơ quá 30 giây không phát sinh dữ liệu.

6.2. Vòng lặp phát khối 16 KiB & Thu hồi quyền tức thì giữa chừng

Dữ liệu được chia thành các khối 16 KiB. Trước mỗi khối được phát đi, hàm isPeerAuthorized(...) được gọi để kiểm tra quyền. Nếu chủ sở hữu file gỡ bỏ quyền của nhóm trong lúc file đang tải dở, quá trình truyền sẽ bị ngắt ngay lập tức với mã lỗi FORBIDDEN.

6.3. Kiểm soát dòng chảy Backpressure và Cam kết file nguyên tử

  • Cửa sổ trượt: Bên nhận gửi gói ack sau mỗi 256 KiB. Bên gửi sẽ tạm dừng luồng đọc đĩa nếu số byte chưa xác nhận vượt quá 512 KiB hoặc bộ đệm socket vượt ngưỡng 256 KiB.
  • Cam kết file nguyên tử: Tải về file tạm .<filename>.tmp.<transferId>, thẩm định mã băm SHA-256 toàn vẹn, rồi dùng lệnh link() để tạo hard link tới file đích. Nếu file đích đã tồn tại, hệ điều hành trả về EEXIST để bảo vệ dữ liệu cũ của người dùng.

7. Nhạc trưởng PeerEngine (src/main/p2p/engine.ts)

7.1. Cấu trúc dữ liệu GroupRuntime và policyQueue

Mỗi nhóm được đóng gói trong một đối tượng GroupRuntime. Mọi hành động can thiệp vào trạng thái mạng đều phải đi qua hàng đợi tuần tự queueAction<T>, loại trừ hoàn toàn các lỗi Race Condition.

7.2. Cân bằng Topo và Giám sát hiệu lực monitorTimer

Định kỳ mỗi 2 giây, monitorTimer kiểm tra tính tươi mới của quyền lực trong nhóm. Nếu mất liên lạc với máy chủ Signaling quá 6 giây (ROSTER_FRESHNESS_LEASE_MS = 6000), vai trò Supernode tự động hết hạn để bảo vệ tính nhất quán của mạng phân tán.
