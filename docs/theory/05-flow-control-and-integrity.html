Theory: Flow Control & Cryptographic Integrity

This document details the sliding-window flow control algorithms, buffer backpressure management, and content-addressable SHA-256 verification pipeline implemented in src/main/p2p/transfers.ts.

1. Flow Control & Congestion Management

WebRTC SCTP data channels provide reliable ordered transmission, but without application-level flow control, fast senders can overwhelm slow receivers, exhaust process heap memory, or trigger socket buffer overflows.

p2p-multiple-groups implements a multi-tiered sliding-window flow control architecture:

flowchart TD subgraph Uploader["Uploader Node"] FS["Filesystem ReadStream\n(highWaterMark: 16 KiB)"] HWM{"bufferedAmount > 256 KiB?"} UNACK{"unackBytes > 512 KiB?"} SCTP["SCTP Data Channel Send Buffer"] FS --> HWM HWM -->|Yes: stream.pause()| PAUSE["Pause Disk Read"] HWM -->|No| UNACK UNACK -->|Yes: await AckGate| WAIT["Wait for Window ACK"] UNACK -->|No| SCTP end subgraph Receiver["Receiver Node"] RECV["SCTP OnMessage Chunk"] ACC["Accumulated Bytes Counter"] ACK_CHK{"accumulated >= 256 KiB?"} SEND_ACK["Send TransferControlMessageV2::ack"] DISK["WriteStream to .tmp.transferId"] HASH["Streaming SHA-256 Digest"] RECV --> DISK RECV --> HASH RECV --> ACC ACC --> ACK_CHK ACK_CHK -->|Yes| SEND_ACK ACK_CHK -->|No| RECV end SCTP -->|"16 KiB Chunks"| RECV SEND_ACK -->|"Ack(acknowledgedBytes)"| UNACK

Protocol Constants

Parameter Constant Value Architectural Purpose
Chunk Size CHUNK_SIZE 16 KiB (16,384 B) Aligned with SCTP MTU to prevent IP fragmentation.
ACK Interval ACK_INTERVAL_BYTES 256 KiB (262,144 B) Cumulative sliding-window ACK frequency; minimizes control overhead.
Max Unacknowledged MAX_UNACK_BYTES 512 KiB (524,288 B) Maximum allowed inflight unacknowledged bytes.
High Water Mark HIGH_WATER_BUFFER 256 KiB (262,144 B) SCTP buffer ceiling triggering stream.pause().
Low Water Mark LOW_WATER_BUFFER 128 KiB (131,072 B) SCTP buffer floor triggering stream.resume().
Stall Timeout STALL_TIMEOUT_MS 30,000 ms (30 s) Watchdog timer detecting stalled or unacknowledged streams.

The Cumulative Sliding-Window ACK Invariant

Instead of acknowledging every 16 KiB chunk individually (which would cause a 1:1 message amplification), the receiver accumulates inbound bytes:

Emit ACK ⟺ ΔBytes_recv ≥ 256 KiB

The uploader tracks unacknowledged bytes:

UnackBytes = Bytes_sent - Bytes_acked

If UnackBytes ≥ 512 KiB, the uploader halts reading from disk until an ACK message arrives from the receiver, strictly bounding maximum inflight memory footprint.

Double-Tier Buffer Backpressure

  1. When channel.bufferedAmount > HIGH_WATER_BUFFER (256 KiB), the sender pauses the local filesystem stream (stream.pause()).
  2. When the kernel flushes the SCTP socket buffer down to LOW_WATER_BUFFER (128 KiB), Werift fires the bufferedamountlow event, resuming filesystem reads (stream.resume()).

2. Cryptographic Integrity & Content Addressability

In untrusted P2P overlays, files must never be identified solely by mutable filenames. p2p-multiple-groups establishes content addressability via cryptographic digests:

FileID ⟹ SHA-256(FileContents)

On-The-Fly Streaming Verification

During download:

  1. Incoming 16 KiB binary chunks are piped simultaneously into the disk staging stream and a Node.js cryptographic hashing stream: 
    hash.update(chunk)
  2. When the uploader dispatches TransferControlMessageV2::end, the receiver closes the file and completes the digest:
    ComputedDigest = hash.digest('hex')
  3. The receiver compares ComputedDigest against the catalog advertisement ExpectedDigest in constant time:
    crypto.timingSafeEqual(ComputedDigest, ExpectedDigest)

Atomic Publication & Staging Invariants

To prevent partial, truncated, or malicious files from being exposed to the host operating system:

  1. Staging File: Downloads are written strictly to a hidden temporary file:
    Path_staging = join(targetDir, ".tmp." || transferId)
  2. Failure Cleanliness: If the connection breaks, the stall timer fires, or the SHA-256 digest fails verification, the staging file is unlinked immediately via fs.rm().
  3. Atomic Commit: Only after verification succeeds does the engine atomically rename the staging file to the destination path using fs.rename():
    rename(Path_staging, Path_final)

    In POSIX and Windows filesystems, rename() within the same volume is an atomic directory entry swap. External applications never observe a half-written file.
