00. JS, TS & npm Fundamentals: A Java Developer's Deep Dive

An exhaustive architectural and syntax mapping guide bridging Java, Maven, Gradle, and JVM mental models directly to modern JavaScript, TypeScript 5.9, Node.js 24, and the electron-vite multi-target build pipeline.

1. Core Ecosystem & Mental Model for Java Developers

Coming from the Java/JVM ecosystem (or C#, Go, and C++), looking at a repository filled with .js, .ts, .tsx, .cjs, package.json, tsconfig*.json, and node_modules/ can feel disorienting. However, almost every concept in the modern Node.js and TypeScript ecosystem has a direct 1:1 equivalent in Java, Maven, and the JVM.

1.1. Java-to-JS/TS/Node/npm Rosetta Stone

Java / Maven / Gradle Concept TypeScript / Node / npm Equivalent Architectural Role & Implementation Details in This Codebase
Source File (.java) src/**/*.ts, src/**/*.tsx Statically typed source code. Files ending in .tsx contain React 19 JSX markup embedded directly inside TypeScript.
Bytecode (.class) Compiled JavaScript (.js, .cjs) Browsers and Node.js cannot execute TypeScript directly. TypeScript relies on Type Erasure: all type annotations, interface, and type declarations are stripped away, producing standard ECMAScript.
JVM (HotSpot Runtime) Node.js >=24.12.0 (V8 + libuv) & Chromium V8 Node.js provides the headless execution runtime (Google V8 JS engine + libuv C library for asynchronous non-blocking event-driven I/O) for the Main process, signaling service, and tests. Chromium V8 executes the UI Renderer process.
Threads & CompletableFuture<T> Single-Threaded Event Loop with Promise<T> & async/await Node.js does not spawn OS threads for concurrency; instead, a single-threaded Event Loop handles microtasks and macrotasks. async/await provides synchronous-looking syntax over asynchronous Promise pipelines.
pom.xml / build.gradle package.json The declarative manifest at the repository root defining package metadata, runtime engine constraints ("node": ">=24.12.0"), task scripts, and library dependencies.
gradle.lockfile / Maven checksums package-lock.json Exact tree of resolved dependencies with cryptographic SHA-512 integrity digests, guaranteeing byte-for-byte reproducible builds across developer machines and CI/CD pipelines.
~/.m2/repository (Local Cache) ./node_modules/ The project-local directory where npm installs third-party dependency packages. Unlike ~/.m2, node_modules is scoped to the repository and is strictly excluded from version control (.gitignore).
Maven <scope>compile</scope> "dependencies" Runtime dependencies packaged into the production application: react@19.3.0, react-dom@19.3.0, werift@^0.24.4 (pure Node.js WebRTC), and ws@^8.21.3 (RFC 6455 WebSockets).
Maven <scope>provided</scope> / test "devDependencies" Tooling and build-time dependencies: electron@44.10.1, electron-vite@5.0.0, vite@7.3.7, typescript@5.9.3, @vitejs/plugin-react@5.2.0, and @types/*.
Stub JARs / C Headers (.h) Type Definition Packages (@types/*) Packages like @types/node, @types/react, @types/react-dom, and @types/ws contain zero executable JavaScript. They are pure .d.ts declaration headers providing static type definitions for libraries written in untyped JS or C++ native bindings.
Maven Plugins (<build><plugins>) "scripts" in package.json + electron.vite.config.ts Build lifecycle task runners. Running npm run build invokes tsc and Vite/Rollup bundling pipelines according to electron.vite.config.ts.
JUnit 5 (@Test, Assertions.*) Node.js Native Test Runner (node:test, node:assert/strict) Zero-dependency built-in testing engine in Node.js 24 using describe(), it(), and assert.strictEqual(), executed directly via node --test.

1.2. Module Systems: ECMAScript Modules (ESM) vs. CommonJS (CJS)

In the modern JavaScript ecosystem, two module specifications exist side by side:

  • ECMAScript Modules (ESM): The official modern JavaScript standard. Configured via "type": "module" in package.json:5, telling Node.js that all .js and .ts files default to ES module syntax (import { x } from './y.js' and export const x = 1).
  • CommonJS (CJS): The legacy Node.js module format using const x = require('./y') and module.exports = { x }. In this project, CommonJS is strictly scoped to out/preload/index.cjs (required by Electron's native browser window manager) and tests/fixtures/electron-profile-launcher.cjs.

1.3. The Two Ways TypeScript Executes in This Project

In this repository, TypeScript follows two decoupled execution pipelines:

Execution Pipeline Applies To Mechanism
Path A: Direct Zero-Build Type Stripping services/signaling/index.ts, scripts/*.ts, tests/**/*.test.ts Node.js >=24.12.0 natively strips TypeScript annotations in memory and executes standard JavaScript directly with zero disk build overhead. Enforced via "erasableSyntaxOnly": true and "rewriteRelativeImportExtensions": true in tsconfig.node.json.
Path B: Bundled Electron Execution src/main, src/preload, src/renderer electron-vite runs Vite, Rollup, and esbuild to transpile JSX, tree-shake dependencies, inject strict CSPs, and bundle assets into ./out/.

1.4. Ground-Truth Data Contracts

All data contracts in the project are enforced at compile time using TypeScript interfaces that undergo Type Erasure. For example, the canonical group invitation contract from src/shared/p2p.ts:22-27 is: 

export interface GroupInvitation {
  version: 2
  signalingUrl: string
  groupId: string
  token: string
}

2. Three-Process Electron Architecture & Three tsconfig Configurations

Electron applications run multiple isolated processes to prevent untrusted UI code from compromising host operating system security:

  • Main Process (Node.js) (src/main/index.ts → out/main/index.js): Owns full OS privileges, file I/O, pure Node.js WebRTC (werift), WebSocket connections (ws), and OS keychain storage via SafeCredentialStore.
  • Preload Bridge (src/preload/index.ts → out/preload/index.cjs): Runs in a protected bridge context with contextIsolation: true, exposing window.p2p via contextBridge.exposeInMainWorld over 22 strictly validated IPC_CHANNELS.
  • Renderer Process (Chromium) (src/renderer/index.html → out/renderer/): Sandboxed React 19 UI with zero Node.js privileges, locked down by p2pCsp (connect-src 'none' in production).

Content Security Policy (CSP) Protection

The custom p2pCsp(isDev) plugin in electron.vite.config.ts:5-17 injects the Content Security Policy into src/renderer/index.html: 

function p2pCsp(isDev: boolean): Plugin {
  const devCsp =
    "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ws://127.0.0.1:5173; object-src 'none'; base-uri 'none'; form-action 'none'"
  const prodCsp =
    "default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'"

  return {
    name: 'p2p-csp',
    transformIndexHtml(html: string): string {
      return html.replace('%P2P_CSP%', isDev ? devCsp : prodCsp)
    }
  }
}

Three tsconfig Configurations

To decouple browser web types from Node.js runtime types, the project uses TypeScript Project References:

  1. tsconfig.json: Root coordinator defining references to tsconfig.node.json and tsconfig.web.json.
  2. tsconfig.node.json: Configures "types": ["node"] for src/main, src/preload, services/, scripts/, and tests/.
  3. tsconfig.web.json: Configures "jsx": "react-jsx" and "types": ["vite/client"] for src/renderer.

Line-by-Line Pipeline Dissection

Build Step Why It Runs & What It Does Key Architectural Details
Phase 1: npm run typecheck Runs typecheck:node and typecheck:web sequentially. Uses tsc --noEmit. Silence signifies success (Unix exit code 0). Zero files are written to disk.
Build 1: out/main/index.js vite building ssr environment... Why SSR? Vite designates any Node.js runtime target as "SSR". Node built-ins and npm dependencies (werift, ws) are externalized. 16 modules in src/main and src/shared are bundled into out/main/index.js (~217.90 kB), matching "main" in package.json.
Build 2: out/preload/index.cjs vite building ssr environment... The Preload script runs in Electron's Node-enabled bridge context. Vite bundles src/preload/index.ts and src/shared/contracts.ts into CommonJS (out/preload/index.cjs, ~4.01 kB). All type imports are erased.
Build 3: out/renderer/ vite building client environment... Why Client? The Renderer runs inside sandboxed Chromium. Vite compiles a browser SPA, bundling React 19 and React DOM:
  1. out/renderer/index.html (~0.62 kB): Production HTML with p2pCsp(false) strict CSP (connect-src 'none').
  2. assets/index-B2QFJOqy.css (~15.37 kB): Extracted, minified CSS.
  3. assets/index-DaQqRAeS.js (~739.87 kB): Minified React 19 app with content-hash suffix.

5. In-Depth Breakdown of All 19 Commands

Below is a comprehensive breakdown of each command's flags, mechanics, and runtime behavior:

Lifecycle & Development

  • npm install: Reads package.json and pins versions via package-lock.json. In CI environments, use npm ci.
  • npm run dev: Runs electron-vite dev --watch. The --watch flag watches files and enables HMR for the React UI.
  • npm run build: Runs npm run typecheck && electron-vite build. Guarantees 0 type errors before producing production bundles.
  • npm run start: Runs electron-vite preview, testing production artifacts in ./out/.

Static Typechecking

  • npm run typecheck:node: Validates tsconfig.node.json using tsc --noEmit --composite false.
  • npm run typecheck:web: Validates tsconfig.web.json for React 19 JSX components.
  • npm run typecheck: Runs both checks sequentially.

Testing Suites

  • npm run test:unit: Executes unit tests for theme-store, credential-store, peer-store-v2, profile-migration, signaling-config, and p2p-protocol.
  • npm run test:p2p: Executes multi-peer P2P integration tests (WebRTC, HRW election, transfer flow control, multi-group isolation, and owner security).
  • npm run test:e2e: Spawns Electron with Chrome DevTools Protocol to verify navigation and the window.p2p sandbox bridge.
  • npm test: Chains all unit, P2P, and E2E suites consecutively.

Signaling & Container Ops

  • npm run signal:start: Runs node --env-file-if-exists=.env services/signaling/index.ts. Loads .env automatically without crashing if missing.
  • npm run signal:invite: Runs scripts/create-invite.ts. Accepts --group-id=<id> and --code-only: 
    npm run signal:invite -- --group-id=general-group --code-only
  • npm run docker:build: Builds p2p-multiple-groups-signaling container image.
  • npm run docker:up: Runs docker compose --env-file .env up -d --build to start containers in background.
  • npm run docker:down: Runs docker compose down to stop and remove containers.

Documentation Tooling

  • npm run docs:open: Opens docs/index.html in default browser.
  • npm run docs:screenshots: Automates headless screenshot capture for documentation assets.
  • node scripts/verify-html-docs.js: Verifies HTML documentation integrity across all 25 pages.

6. Practical Step-by-Step Workflows

Workflow 1: First-Time Setup & Development Launch

# 1. Clone repository
git clone https://github.com/your-org/p2p-multiple-groups.git
cd p2p-multiple-groups

# 2. Install dependencies
npm install

# 3. Typecheck codebase
npm run typecheck

# 4. Launch in development mode
npm run dev

Workflow 2: Running a Local 2-Peer Swarm on One Machine

# TERMINAL 1: Launch Signaling Server
cp .env.example .env
npm run docker:up
# Or run directly: npm run signal:start

# TERMINAL 2: Launch Peer A (Development Mode)
npm run dev
# 1. Open "Network & Groups" -> Select "Create Group" -> Enter name (e.g. "alpha-swarm")
# 2. Click "Create & Join" -> Peer A is elected Owner and Supernode
# 3. Click "Copy Invite Code" (or copy V2 JSON invitation)
# 4. Open "Library" -> Click "Add File" -> Select a file and check "alpha-swarm" to share

# TERMINAL 3: Launch Peer B (Production Preview Mode)
npm run build
npm run start
# 1. Open "Network & Groups" -> Select "Join Group"
# 2. Paste Invite Code copied from Peer A -> Click "Join Group"
# 3. Open "Search & Discovery" -> Search for file shared by Peer A
# 4. Click "Download" -> Open "Transfers" to observe 16 KiB chunk flow over WebRTC!

Workflow 3: Pre-Flight Verification Before Committing

# Step 1: Ensure zero TypeScript errors
npm run typecheck

# Step 2: Execute all 16 test suites
npm test

# Step 3: Verify HTML documentation integrity
node scripts/verify-html-docs.js
